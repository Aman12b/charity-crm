# Non-Functional Requirements

## Security (SEC)

**NFR-SEC-01 – Server-side authorization**
All permissions from the matrix in REQUIREMENTS §3 are enforced in the backend via authorization policies.
Every endpoint has an explicit policy; there is no endpoint without `RequireAuthorization` except login and health.
Unauthorized role → `403`, unauthenticated → `401`.

**NFR-SEC-02 – Session security**
Cookie-based authentication: `HttpOnly`, `Secure` (when served over HTTPS), `SameSite=Strict`.
Anti-forgery protection for all state-changing requests (double-submit token via header `X-XSRF-TOKEN`).
ASP.NET Data Protection keys are persisted to a Docker volume so sessions survive container restarts.

**NFR-SEC-03 – Password policy**
Minimum 10 characters, at least one letter and one digit. Hashed with ASP.NET Core Identity defaults (PBKDF2).

**NFR-SEC-04 – Input validation & injection**
All input validated server-side. Database access only through EF Core (parameterized). No raw SQL with string concatenation. React escapes output by default; `dangerouslySetInnerHTML` is forbidden.

**NFR-SEC-05 – Secrets**
No secrets in source code or images. Configuration via environment variables / `.env` (excluded from git).

**NFR-SEC-06 – Security headers**
nginx sets `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`.

**NFR-SEC-07 – Rate limiting**
Login endpoint limited to 10 requests per minute per IP (ASP.NET Core rate limiter).

## Data protection (DATA)

**NFR-DATA-01** – Only data fields defined in the requirements are stored; no tracking or analytics.
**NFR-DATA-02** – Personal data is not written to application logs (log IDs, not names/emails).
**NFR-DATA-03** – All timestamps stored in UTC, displayed in `Europe/Vienna`.

## Reliability (REL)

**NFR-REL-01 – Transactions**
Recording a payment, allocating the invoice number, creating the invoice and enqueuing the email happen in one database transaction (outbox pattern). Either all succeed or none.

**NFR-REL-02 – Email decoupling**
Email sending runs in a background worker. SMTP outages do not affect any user-facing operation.

**NFR-REL-03 – Concurrency**
Invoice numbers are allocated with a row-level lock so concurrent payments never produce duplicate or skipped numbers. Members and users use optimistic concurrency (row version); conflicting edits return `409` with a clear message.

**NFR-REL-04 – Backup**
A documented `pg_dump` based backup/restore procedure (script in `scripts/`), including the invoice PDF volume.

## Performance (PERF)

Sizing assumption: up to 5,000 members, 100,000 payments, 10 concurrent users.
**NFR-PERF-01** – List and search requests respond in < 500 ms (p95) at this size.
**NFR-PERF-02** – PDF generation < 2 s per invoice.
**NFR-PERF-03** – All lists are server-side paginated; indexes on search and filter columns.

## Usability (UX)

**NFR-UX-01** – UI completely in German; dates `dd.MM.yyyy`, amounts `1.234,56 €`.
**NFR-UX-02** – Responsive, desktop-first; usable down to 768 px width.
**NFR-UX-03** – Navigation shows only features the user's role may use.
**NFR-UX-04** – Clear feedback: loading states, success notifications, field-level validation messages, confirmation dialogs for de-registering, deactivating and cancelling.
**NFR-UX-05** – Basic accessibility: keyboard navigable, labels on all form fields, sufficient contrast (WCAG 2.1 AA as target).

## Maintainability (MAINT)

**NFR-MAINT-01** – Layered backend (Api / Core / Infrastructure) with dependencies pointing inward.
**NFR-MAINT-02** – Unit tests for all services in Core; integration tests for every endpoint including authorization (403) cases.
**NFR-MAINT-03** – No compiler warnings; `TreatWarningsAsErrors` in backend; ESLint + Prettier in frontend.
**NFR-MAINT-04** – OpenAPI document generated by the API; Scalar UI available in Development only.

## Operations (OPS)

**NFR-OPS-01 – Docker-ready**
The full stack starts with a single `docker compose up --build`. No manual steps besides creating `.env`.

**NFR-OPS-02 – Migrations**
EF Core migrations are applied automatically on API startup.

**NFR-OPS-03 – Health checks**
`GET /api/health` reports API and database status; used by Docker healthchecks.

**NFR-OPS-04 – Logging**
Structured JSON logging to stdout (Serilog). Log level configurable via environment variable.

**NFR-OPS-05 – Configurable mail transport**
SMTP host, port, credentials, TLS and sender address are configurable. Default: Mailpit. Switching to a real SMTP relay (e.g. Brevo, Mailjet) requires only environment changes.

**NFR-OPS-06 – Images**
Multi-stage Dockerfiles, minimal runtime images, containers run as non-root user.
